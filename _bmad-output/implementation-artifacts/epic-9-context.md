# Epic 9 Context: Review, Challenge, Baseline and Decision Trace

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

Close the Release 1 estimation loop with human governance and auditability. Named engineering, PM and security reviewers approve, reject or challenge a submitted Estimate Version. A Challenge reruns only the affected Assessments and produces a new Estimate Version with the delta, leaving the old one intact. Once every requested review is approved and nothing blocks, the presales engineer sets the Baseline: the single approved figure that no agent or run can quietly overwrite. Anyone with access can then trace any Estimate line or Assumption back to its Findings, Evidence and human decisions, and compare any two versions. The result is a complete, tamper-proof answer to "how did we arrive at this number?".

## Requirements & Constraints

- **Review Requests** go to named reviewers who hold the role matching the review type (`engineering | pm | security`). The server enforces reviewer authorization and blocks self-approval by the version's author, whatever the UI shows. Decision actions: approve, reject, challenge, request evidence, request alternative, escalate. Every action except approve needs a reason. Overdue pending requests get in-app reminders (default every 3 days, `PSA_REVIEW_REMINDER_DAYS`). Teams and email delivery are R2 (Epic 11).
- **Challenge** needs a reason. In R1 the platform suggests the affected Assessments by deterministic rules, and the owning presales engineer confirms which to rerun (automatic rerun only arrives in R3). Conflict detection, Critic and Red Team always run again. The rerun produces a new version showing the delta, and the previous version and the Challenge stay preserved.
- **Baseline** can be set only when the version is `approved`, at least one Review Request was sent and every non-cancelled one is approved, and the single submission-blocker check returns nothing. Setting it is traced with the approvers. Only a newer approved version can replace it. No Workflow Run, Agent or system actor may set or overwrite it.
- **Decision Trace** records, per Estimate Version, the Requirements, Evidence, Assessments (with config versions), Critic and Red Team Findings, Conflicts and resolutions, overrides, Challenges, review decisions and the Baseline approval, each with actor and timestamp. It stores decisions and Evidence only, never prompts, model reasoning or chain-of-thought. Trace rows can't be edited or deleted by anyone, admins included.
- **Exploration:** any user with access can go from any Estimate line or Assumption to the Findings, Evidence and human decisions behind it, and compare any two versions. Sales representative collaborators get read-only lineage and can't request reviews. Users without access get the standard no-access response.
- **Performance:** the first Trace page, with any single filter, responds within 500 ms at P95 on an Opportunity with 5,000 events.
- **Retention:** the trace is append-only and kept for the contract lifetime plus 7 years. Only the controlled purge job may delete.

## Technical Decisions

- **Ownership:** `reviews` owns `reviews_review_requests`, `reviews_review_decisions` (append-only; request status is derived from the latest decision), `reviews_review_replies` and `reviews_challenges`. `estimates` owns `estimates_baselines` (insert-only history, written only by `estimates.set_baseline`). `notifications` owns `notifications_notifications` (the Inbox). Reviewer read access is an Opportunity collaboration with a `reviewer` role, owned by `opportunities`. Cross-module calls go only through each module's `application/public.py`.
- **Mutation path:** every command runs `identity.authorize`, checks domain state-machine rules, checks `row_version` (If-Match, 412 on mismatch), writes, and calls `platform.trace.append(uow, …)` in one Unit of Work. Notifications are created through `notifications.public.notify(uow, …)` inside the caller's UoW. The channel port has only an in-app adapter for now.
- **State machines (domain-enforced, with transition tests):** Review Request `pending, approved, rejected, challenged, superseded, cancelled`. Challenge `awaiting_confirmation, reassessing, completed, declined, failed`. Estimate Version `draft, submitted, in_review, approved, rejected, superseded`. Opportunity status (`baselined`) is derived by a query and never stored.
- **Typed, versioned targets:** review targets are `{kind: estimate_version | assessment, id, version}` (`proposal` is added in R2). Challenge targets are `{kind: finding | assessment, id, version}`, with the Finding's Assessment version. Evidence is `{kind, id, version?, span?}` and must resolve, or the write is rejected.
- **Supersession:** submitting a newer version supersedes earlier non-Baseline submitted versions. In the same UoW, `reviews.public.supersede_open_requests` marks their pending and challenged requests `superseded`. Approvals never carry over to a new version.
- **Challenge run:** confirmation calls `workflows.start_run(run_type=challenge, trigger_ref=challenge_id)` with the idempotency key `run:<opportunity_id>:challenge:<challenge_id>`. The plan covers the confirmed Assessments, then Conflict detection, then the Critic and Red Team. Unconfirmed Assessments are reused. Challenge context goes to agents inside a delimited data block. Only the run's final node creates the new version, via `estimates.create_version` with the `node:<run>:<task>:<attempt>` idempotency key and `expected_parent_version_id`, so a run started on a stale version fails cleanly.
- **Serialisation:** the shared `platform.locks.opportunity_lock(uow, opportunity_id)` helper (a bigint key from the UUID, then `pg_advisory_xact_lock`) is taken by `set_baseline`, review decisions, and every command that affects blockers. A Postgres test proves a Baseline is never set on a version with a rejected request.
- **Single blocker check:** `estimates.get_submission_blockers(version)` is the only gate for submit and Baseline. Its Review Request category reads from `reviews.public.list_open_requests(version)`. A failed Baseline returns 409 problem+json `baseline_blocked`, listing blockers by type.
- **Trace:** `platform_trace_events` is written only through `platform.trace.append`. The app DB role has no UPDATE or DELETE on it. Every `event_type` has a Pydantic payload model in `platform/trace/catalogue.py`, and CI asserts both that full coverage and that no payload has prompt or reasoning fields. Names: events are `<module>.<entity>.<past_tense_verb>`, actions are `<module>.<entity>.<verb>`, jobs are `<module>.<verb>`.
- **Lineage queries:** `estimates.get_line_lineage` and `estimates.get_assumption_lineage` compose public queries from `assessments`, `conflicts`, `intake`, `gaps` and `reviews`. They never read another module's tables.
- **Reminders:** the daily `reviews.send_reminders` job runs from `platform_schedules`, with the idempotency key built from the request ID and the interval number.
- **Live updates:** there is one SSE stream per Opportunity and no per-user stream. The Inbox refreshes on window focus and polls every 30 s.
- **Errors:** problem+json, with codes such as `reviewer_not_authorized_for_type`, `reviewer_not_authorized`, `self_approval_forbidden` and `baseline_blocked`.
- **Testing:** domain logic is tested without a DB or LLM. Commands and graphs get Postgres integration tests with a fake ModelGateway. An end-to-end fixture, from intake through Set Baseline, backs both the lineage test and the trace completeness test.

## UX & Interaction Patterns

The 2026-10-21 redesign spec (`new-mockups/Presales Agent Design Spec (standalone).html`) is authoritative. The older `mockups/` folder is superseded.

- **Review panel** (Inspector, and "Open in tab" for full width): shows the author's message and the target with its Evidence chips, plus the diff against the previous version for an Estimate. **Approve**, **Reject** and **Challenge** sit in the first row, with **Request evidence**, **Request alternative** and **Escalate** as a second row of buttons. Approve is disabled for the author, with an explanatory message. The author's own request shows a **Review outcomes** list (icon, who, what, time, note). When everything is approved, the panel reads "All requested reviews approved. Baseline can be set." and offers **Set Baseline**.
- **Challenge dialog:** a single 520px dialog with a required reason ("State what looks wrong and why.") and "Assessments to rerun" toggle cards (`aria-pressed`; Suggested pre-ticked, Optional unticked). A reviewer sees the cards read-only and a **Raise Challenge** button. The owner gets editable cards, a **Rerun N Assessments** button and **Decline**.
- **Inbox** (`g i`): two panes, with groups for Review Requests, Challenges, runs waiting for input and decision updates. Rows use `j`/`k` and `Enter`, are paginated, show an unread dot and a kind pill, and are marked read on open. The empty state reads "Nothing waiting for you." with no illustration. Superseded items are greyed out with a "Superseded by vN" link and no actions.
- **Set Baseline confirm dialog:** titled "Set Baseline for Estimate v3?", it lists approvers with role or review type and approval time, and warns that the action can't be undone and only a newer approved version replaces the Baseline. The "Blockers to Baseline" gate on Overview updates live, and when it reads "0 blockers to Baseline", Set Baseline becomes primary. The Baseline marker (anchor icon) appears everywhere versions are listed, and the switcher lists the Baseline first. A polite live region announces Baseline changes.
- **Version lifecycle card** (Draft, In review, Approved, Baseline) is a read-only status view derived from version status plus the Baseline pointer, with one sentence for the selected version. Switcher segments carry Superseded, Baseline or Draft pills.
- **Trace tab** (`8`): a reverse-chronological, append-only list (time, actor, plain-words event, subject link), paginated, with `j`/`k` and `Enter`. Filters cover version, subject, actor type and event type, and the filter state lives in the URL. Selecting a row opens the **Trace event Inspector** automatically: Payload (Event, Actor with agent version, Subject, Estimate Version, then Correlation ID and Model for an agent, or Reason and authorising permission for a human), a "Version comparison · vX to vY" with `+`/`−` rows for line edits, Evidence chips, and the note "Trace rows are append-only. Model reasoning is not stored, only decisions and Evidence." The empty state reads "No trace events" and links to Overview.
- **Lineage and compare:** the design spec has no dedicated lineage-inspector screen. Build it in the Inspector pattern (a Lineage section on the Estimate line or Assumption, Evidence chips, **Open in Trace** to the filtered Trace tab). Superseded references are struck through, labelled "superseded", and still open the cited version. The spec shows only a "Diff vs previous" toggle (`d`). Compare-any-two-versions uses the standard diff view: tint plus `+`/`−` markers, a delta column ("+x h", "−x h", "no change"), and a "Why it changed" list of the trace events between the two versions.
- **Shared states:** an inline 412 alert ("Changed by [user] since you opened it", with **Reload** and **View diff**). Skeletons show for at least 150 ms. Disabled primary actions are `aria-disabled` and state their reason in adjacent text.

## Cross-Story Dependencies

- **Within the epic:** 9.1 (requests and Blockers to Baseline) is the base for 9.2 to 9.7. 9.2's Inbox carries the items for 9.3 to 9.6. 9.3 records decisions and is the Challenge entry point that 9.5 builds. 9.4's supersession is reused by 9.6. 9.5 starts the run that 9.6 executes. 9.7's shared lock helper is also used by 9.3's decisions. 9.8's Trace tab and inspector are the target of 9.9's "Open in Trace". 9.10 reuses 9.9's lineage test on a full end-to-end fixture.
- **Earlier epics:** this epic relies on the platform UoW, authorize, trace and roles (Epic 1), and on Evidence chips and the Source viewer (Epic 2). It needs Workflow Runs, waits and idempotent starts (Epic 5), and Conflicts, Critic, Red Team and Finding overrides (Epic 6). From Epic 8 it uses Estimate Versions, `create_version`, `submit_version`, `get_submission_blockers`, the Assumptions Register, the version switcher and the diff toggle. Story 9.7 replaces the direct advisory-lock calls in Stories 4.4, 4.7, 6.6, 8.4, 8.5 and 8.6. Epic 17's token layer and primitives (17.1) must precede any new UI.
- **Later epics:** Epic 11 adds policy approvals (FR-39) as an extra Baseline check, plus Teams and email channels on the notification port. Epic 12 generates Proposals from the Baseline and adds `proposal` review targets. Epic 15 promotes Scenarios through `set_baseline` and makes Challenge reruns automatic. Epic 10 traces overruns through the lineage built here.
